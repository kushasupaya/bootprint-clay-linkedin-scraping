# Decisions

## 2026-10-26

- **Build one feature at a time: history website first, then Clay, then Slack.** The user chose this order. Not chosen: starting with the Clay or posts path, because the page and log format are the foundation both reuse.
- **Log line format is the contract between pipeline and page:** `time | person | source | decision | what happened | link`. Chosen because it is human-readable (plan requirement) and lets the page group by person. Not chosen: JSON logs, which a non-technical user can't read.
- **Page stack: Python standard-library server plus plain HTML/CSS/JS, no build step.** Chosen for zero install and a read-only surface (405 on writes). Not chosen: a framework, which adds dependencies for a five-person page.
- **Visual direction: cool slate palette, Schibsted Grotesk, roster plus per-person timeline, 14-day activity strip.** Avoids the cream/terracotta and dark/neon defaults. User approved.
- **Watchlist stays hand-edited, not fed from Clay; joined to Clay by LinkedIn URL.** This keeps the roster intact if Clay is down or returns blank data and stops stray Clay rows from creating alerts. Not chosen: Clay as the roster (simpler, but loses those safeguards) or an add-person form (would break read-only).
- **Clay delivery: leaning to a Google Sheet that the laptop reads, else a small always-on mailbox the laptop pulls from. Not final.** Clay cannot reach a sleeping laptop, so a direct webhook or tunnel is rejected. Open until the user confirms their Clay setup.

## 2026-10-26 (later)

- **Posts path (Gmail bell emails, post labeling) is parked; version 1 detects job changes through Clay only.** The user checked and LinkedIn has no email option for these notifications (job-change notifications are in-app and push only). Not chosen: reading phone pushes or scraping LinkedIn, because code can't read pushes reliably and scraping risks the user's account and breaks LinkedIn's terms. Revisit only if Clay can return post text. This supersedes the posts-path plan in `plan.md` (note added there).
- **Clay data reaches the engine through the Google Sheet Clay fills; the laptop will read the sheet directly later.** For now the user downloads a CSV to `data/clay_latest.csv`. Preferred live access is a read-only Google service account; "publish to web" is a stopgap only, because the link exposes candidate names to anyone who has it.
- **The Clay timestamp column ("Last Enriched") is first-class.** Per person the newest row wins, rows older than 48 hours are Skipped (so a stalled Clay refresh never looks like "no change"), and the timestamp is shown in every log line, in memory (`data_as_of`) and on the page. Not chosen: ignoring timestamps, which hides stale data.
- **Title and org are cleaned inside the engine, not in the CSV.** Titles lose a trailing "at Employer"; orgs lose a trailing "(branch)" and ", City" or ", ST". Both incoming and saved values are cleaned before comparing, so old memory causes no false alarms and heals to the clean value. Legal suffixes and "&" names are kept. Not chosen: editing the CSV (Clay overwrites it every refresh). Tradeoff: a move between branches of one company is not reported.
- **Real data replaced the sample data.** The made-up watchlist, memory and log were archived in `sample/`; `watchlist.json` now holds the five people from the user's sheet and the baseline run is saved. `sample/clay_latest.json` is test input only.
- **The CSV timestamps are currently random (demo only).** The original export is kept at `data/clay_latest.original.csv`. Replace with a real export before trusting any result.

## 2026-10-26 (design pass and refresh button)

- **Light-only vivid design; dark mode removed.** The user found dark mode too much. Electric-blue header band and accents, colored initials avatars; the violet Possible move and red Skipped/stale colors were kept at the user's request.
- **Repeated routine checks collapse into one row per day.** Consecutive No change, Skipped, Error or Ignored entries become "No change (4 checks)" with a toggle to expand; signals are never collapsed. Chosen over hiding routine checks or deleting log lines, so the full log stays intact (plan: log every decision). This is done on the page only.
- **The page is no longer purely read-only: a "Check for updates" button runs the engine on demand** (Clay sometimes updates before the 10 PM run). This supersedes the earlier read-only-page decision. Guardrails: one endpoint (`POST /api/refresh`), localhost only, rejects wrong host/origin or a missing custom header so another website can't trigger it, one run at a time, runs are labeled "manual refresh" in the log. Not chosen: a separate CLI-only refresh, which the user didn't want. For now the button re-reads `data/clay_latest.csv`; it will fetch the Google Sheet once that is connected.
- **Moved `slugify` to `common.py`** so `server.py` can import `engine.py` without a circular import.

## 2026-10-26 (git)

- **Real contact names and employers are kept out of git, including docs and tests.** Docs refer to "one person" and tests use made-up companies; `watchlist.json`, `data/` and `logs/` are gitignored, while `sample/` (made-up) is committed. Chosen because the repo may be visible to others and the plan says candidate data stays local. Not chosen: relying on `.gitignore` alone, since names had leaked into the handoff docs and tests.

## 2026-10-27 (outreach email)

- **Outbound email with a human approval gate, on the page first, Slack later.** The user wants to email a watched person who has moved. This supersedes the plan's "read-only, no contact" rule. Nothing sends automatically: the page shows a template draft, the user edits it and clicks Send (with a confirm dialog). Chosen over auto-send because a wrong "Possible move" would email someone about a move that didn't happen.
- **Gmail SMTP with an app password.** Stdlib only, simple setup. Not chosen: Gmail API (needs a Google Cloud project and OAuth), mailto links (user wanted sending from the tool).
- **The recipient's email comes from Clay** (an Email column), saved in `data/memory.json`. The send endpoint reads the address from memory, never from the request, so the page can't be used to mail an arbitrary address. A blank Email never erases a saved one.
- **Template draft, edited by the user, not AI-written.** No API key or cost. A draft containing "[Your name]" can't be sent, so set `SENDER_NAME` in `.env`.
- **One email per signal.** The sent state is read from the log (`Email | Info | Sent ...` after the signal's time), re-checked under a lock so a double click can't send twice. Not chosen: a separate sent-state file, to keep the log the single source of truth.
- The Slack approval flow reuses `outreach.py` and is not built.
- **Candidate brief and priority tiers (2026-10-27).** The user asked for a brief and a tier list so the recruiter emails Tier A first. No rubric was given, so tiers use recency and signal strength only (A: Job change within 7 days; B: older Job change or recent Possible move; C: older Possible move), because those use only data the system actually has and are easy to explain. Per-person override via `"tier"` in `watchlist.json` rather than a new write endpoint. Not chosen: scoring by seniority or employer, which needs a rubric from the user. Age counts from when the system logged the signal, since Clay doesn't give the date of the change.
- **Demo mode is a separate folder with simulated sending (2026-10-27).** The user wants fake job changes for a presentation. They live in `demo/` (built by `demo.py`, gitignored) rather than in the real log, so real history is never polluted. The demo reuses real contacts' names and addresses, so Send is simulated in demo mode (logged as not actually sent); a real email about an invented move must be impossible. Not chosen: injecting fake lines into `logs/run.log`, which would corrupt real history and could be emailed for real.
- **Demo controls are demo-mode-only endpoints (2026-10-27).** To make the presentation interactive, `POST /api/demo/simulate` and `/api/demo/reset` exist only when `WATCHLIST_DEMO` is set (405 otherwise) and only write inside `demo/`. Simulating a move also updates the demo Clay CSV so a later refresh doesn't undo it. This extends the earlier rule against extra write endpoints, with the demo/real separation as the guardrail. Seven invented candidates were added to the demo so more of it is fake, not just real contacts.
- **Test mode sends for real, but only to the user's own inbox (2026-10-27).** The demo simulates sending, so it can't prove Gmail works. Test mode uses 4 invented candidates whose addresses are `you+name@gmail.com`, so a real send is safe and visible. Not chosen: sending test mail to the real contacts' addresses, or to example.org addresses, which would bounce and prove nothing.
- **Tier rule is recency-based, user may replace it (2026-10-27).** (Recorded earlier today; unchanged.) The 14-day activity strip was kept but made neutral and animation-free at the user's request ("too much"); chosen over deleting it so the "when did something happen" glance stays. Not chosen: removing the strip.

## 2026-10-27 (git history)

- **Six focused commits, pushed to a new branch instead of force-pushing (2026-10-27).** The user asked for proper commit messages after the work had been pushed as one commit. Rewrote local history into six commits grouped by file (server and page changes could not be split by hunk without interactive staging), then pushed to `handoff-2026-10-27`. ## 2026-10-28 (Slack digest)

- **The digest is built from the log, anchored on the last sent digest (2026-10-28).** `digest.py` includes every signal logged after the last `Slack | Info | Sent daily digest` line. This makes "reported signals never repeat" and "a failed send is retried" both fall out of one rule, and covers signals found by manual refreshes during the day. Not chosen: using only the engine's return value from the current run (a failed send, or a manual refresh earlier in the day, would silently drop the signal from Slack).
- **Bot token + member ID, plain `urllib`, no Slack SDK (2026-10-28).** Matches the stdlib-only rule. A bot DMs a user by posting to their member ID with `chat:write`. Not chosen: an incoming webhook (can't DM a person, only a channel), or Socket Mode/interactivity (needed only for the approve button, which is not built).
- **The digest does not mention emailing from Slack.** It links to the local history page for drafting and sending. Slack approval of outreach stays unbuilt.
- **Slack only alerts on changes from the last 48 hours; the page keeps everything (2026-10-28).** The user wants Slack silent about stale data while the website, which the recruiter keeps watching, keeps showing every change with its tier. So `digest.collect` ignores events older than 48 hours (measured from when the system logged the signal, because the real Clay export has no "Last Enriched" column; it matches the engine's 48-hour stale rule), and the omission is logged so nothing is dropped silently. Tiers are untouched (A still means a Job change within 7 days), so a Tier A person can be on the page but not in Slack. Replaces the earlier "first digest looks back 7 days" rule. Not chosen: also filtering the page or lowering tiers, which the user ruled out.

## 2026-10-28 (demo, themes, layout)

- **The demo's Slack alert really sends, to the user's own DM only (2026-10-28).** The user said they will filter demo messages out by hand later, so the demo does not need a fake send. Safeguards kept: the recipient is `SLACK_USER_ID` from `.env`, never the request; `demo.py` copies only the two Slack keys (not Gmail) into `demo/.env`; every demo message starts with "[Demo]" and ends with a "made up" line. This is a narrow exception to "demo never contacts anyone": email to real contacts stays simulated. Not chosen: a preview-only demo (user wanted the real message), or letting the page pick a recipient.
- **Demo shows a preview card before sending (2026-10-28).** `GET /api/demo/slack` draws the exact digest as a Slack-style card; `POST` sends. Not chosen: send on click with no preview, which gives the presenter nothing to talk through.
- **Demo roster trimmed to 13 people, 3 Tier A, and driven by one `SCENARIOS` table (2026-10-28).** The user asked for a cleaner demo with changes to existing people, not new names. Fewer Tier A makes the story easier to follow. Not chosen: adding new invented candidates (user ruled it out), or keeping the position-keyed tables and global state.
- **Dark mode: bulb-icon toggle, saved choice, else system setting, neutral gray palette (2026-10-28).** First version was navy and the user said it was too blue. Every color is a CSS variable; `--job-fill`/`--maybe-fill` are separate from the text colors because one dark value cannot serve both a white-text fill and text on a card. Not chosen: a media-query-only dark mode (no toggle), or hard-coded dark overrides.
- **People list collapses to an avatar rail, desktop only (2026-10-28).** Chosen over hiding the list completely so you can still pick someone and see who has a signal (green/purple ring). Name text is hidden visually but kept for screen readers. Phones keep the list/person switch. Collapsing clears the search so a hidden filter can't mislead.
